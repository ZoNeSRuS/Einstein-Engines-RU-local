# Department Reward Consoles — Design & ТЗ

## Design Document

### Цели и рамки
- Ввести departmental reward консоли, которые мотивируют отделы на выполнение задач в течение раунда.
- Каждая консоль жёстко привязана к банковскому счёту своего отдела (`NT-Cargo`, `NT-Engineering`, `NT-Medical` и т.д.).
- На табло всегда активна только одна задача; после подтверждения она немедленно сменяется следующей.
- Внутри задач поддерживаются рандомизированные плейсхолдеры (например, `driveName = Сингулярность/Тесла`), чтобы сценарии ощущались свежими.

### Анализ аналогов
- **Cargo Bounty Console** (`Content.Server/Cargo/Systems/CargoSystem.Bounty.cs:36`, `Content.Client/Cargo/UI/BountyEntry.xaml.cs:42`) уже реализует очереди задач, BoundUI и проверки доступа. Этот опыт используем для сетевого протокола, UI и кулдаунов, но исключаем физические бирки и проверки контейнеров.
- **EconomyBankAccountSystem** (`Content.Server/AWS/Economy/Bank/EconomyBankAccountSystem.cs:112`) обслуживает банковские счета, зарплаты и транзакции. Опираемся на его API для переводов, списки аккаунтов (`Resources/Prototypes/AWS/Economy/sallaries.yml`) и экономические логи.
- Системы Oracle/Roboisseur доказывают, что ручное подтверждение задач работает. В нашей версии награда всегда денежная и переводится напрямую между счетами.

### Пользовательские сценарии
1. Инженерная консоль выдаёт стартовую задачу «Перезапустить ДАМ щита». Старший инженер вставляет карту капитана или Представителя Корпорации (ПК), подтверждает выполнение, `NT-CentCom` переводит награду на `NT-Engineering`, после чего запускается 15‑минутный кулдаун до Mid-задачи.
2. Cargo получает позднюю задачу «Соберите 3 экспедиционных ящика», завершают её, получают фиксированную награду и ожидают 15 минут до последней Late-задачи.
3. Капитан сталкивается с невыполнимой задачей, фиксирует провал: консоль списывает штраф (сумма выше указанной награды) со счёта отдела, задаётся 30‑минутный кулдаун, после которого стадия повторно выдаёт новую задачу.

### Системное поведение
- На запуске станции формируется группа консольных сущностей — по одной на каждый обслуживаемый отдел. Список отделов берём из реестра банковских счетов станции (`NanotrasenDefaultSallaries`). Привязка `DepartmentRewardConsoleComponent.AccountId` указывает конкретный счёт отдела.
- Задачи описываются прототипами `DepartmentRewardTaskPrototype`, распределёнными по отделам и стадиям. Каждый прототип хранит вес, фиксированную награду, ключ локализации и словари вариантов (например, `driveName`, `targetCount`).
- Стадия — это очередь из трёх шагов: Start → (КД 15 минут) → Mid → (ещё 15 минут) → Late. Таймеры запускаются после подтверждения предыдущей задачи; глобальное время раунда не учитывается.
- Состояние (`DepartmentRewardConsoleState`) включает активную задачу, выбранные варианты, стадию, награду, таймеры подтверждения/пропуска и историю последних выполненных задач. Сервер фиксирует конкретные вставки, чтобы UI и логика совпадали.
- После подтверждения: логируется событие, `NT-CentCom` переводит деньги на счёт отдела, история пополняется, запускается очередной таймер и выбирается задача следующей стадии. При пропуске задача снимается без награды и тут же заменяется новой из текущего пула.

### Экономика и ограничения
- Платёж выполняется через `EconomyBankAccountSystem.TryTransfer("NT-CentCom", AccountId, rewardAmount)`. Система проверяет, что целевой счёт активен и не заблокирован.
- Сумма награды фиксирована в прототипе; игроки всегда видят конкретное число без применения глобального множителя `SalaryMultiplier`.
- Подтверждение и пропуск доступны только картам капитана или Представителя Корпорации. Проверка доступа выполняется через `AccessReaderSystem.IsAllowed`.

### UI/UX
- `DepartmentRewardConsoleWindow` стилизован под AWS-терминалы: блок текущей задачи, стадия и таймер, награда с иконкой, история последних трёх задач, кнопки «Подтвердить» и «Пропустить».
- Вставка карты повторяет UX банковских терминалов (drag-drop или `UseInHand`). При недостатке доступа выводится popup.
- Локализация — `Resources/Locale/ru-RU/aws/department_rewards.ftl` и en-US.

### Риски и вопросы
- Маппинг консолей берёт на себя level-дизайнер; здесь описывается только логика.
- Подтвердить, остаются ли у капитана и ПК эксклюзивные права или список ролей расширяется.
- Нужны анти-abuse механики: кулдаун пропуска, защита от спама задач, логирование.

## Техническое задание

### 1. Общие положения
Создать `DepartmentRewardConsoleSystem`, UI и прототипы задач, обеспечивающие цепочку Start → Mid → Late для каждого отдела и перевод наград со счёта `NT-CentCom` на счёт отдела.

### 2. Функциональные требования
- **Компоненты**
  - `DepartmentRewardConsoleComponent`: `AccountId`, текущая задача, стадия (0/1/2), таймер следующей стадии, таймер пропуска, слот карты, история.
  - `DepartmentRewardTrackerComponent`: список уже выданных задач, защита от повторов.
- **Прототипы**
  - `DepartmentRewardTaskPrototype`: `id`, `department`, `stage`, `weight`, `rewardAmount`, `descriptionKey`, `variants`, `requirements`.
  - Хранение — `Resources/Prototypes/AWS/Economy/department_rewards.yml`.
- **Логика**
  - На станции спавнятся консоли по списку счетов; каждая получает стартовую задачу.
  - Подтверждение запускает перевод, логирование и подготовку следующей стадии после 15‑минутного КД.
- Кнопка «Сдать невыполнимо» доступна тем же ролям, что и подтверждение. При её использовании начисляется штраф (выше награды), деньги списываются с отдела, а стадия переходит в 30‑минутный кулдаун перед повторной попыткой.
  - Всего за раунд доступно три задачи (Start, Mid, Late); после Late консоль считается завершённой.

### 3. Нефункциональные требования
- Все операции выполняются в один серверный тик; максимум одна банковская транзакция на подтверждение.
- Прототипы можно обновлять без перекомпиляции.
- BoundUI синхронизируется диффами; реакции < 100 мс.

### 4. Таймеры и CVAR
- `aws.departmentRewards.stageCooldown = 900` (сек) — пауза между стадиями.
- `aws.departmentRewards.failCooldown = 1800` (сек) — задержка после признания задачи невыполнимой.
- Повторения цепочки нет: после Late консоль блокируется до конца раунда.

### 5. Прототип задачи
```yml
- type: departmentRewardTask
  id: DR-ENG-BUILD-ACCEL
  department: NT-Engineering
  stage: Late
  weight: 5
  rewardAmount: 3500
  descriptionKey: build-drive-task
  variants:
    driveName:
      - Сингулярность
      - Тесла
  requirements:
    - BuildSingularityEmitter
```
`build-drive-task = Постройте {$driveName} двигатель и удерживайте его активным не менее 60 секунд.`

### 6. UI и сеть
- `DepartmentRewardConsoleBoundUserInterface`, `DepartmentRewardConsoleState`, сообщения `Claim`, `Skip`, `InsertCard`.
- UI блокирует кнопки без карты или в кулдауне; ошибки показываются popup-ами.

### 7. Тестирование
- Unit: выбор задач по весам, отсутствие повторов, корректный переход стадий, обработка пустых пулов.
- Интеграция: подтверждение с переводом, отказ без доступа, логирование.
- UI: отображение таймеров, истории, локализации.

### 8. Внедрение
- Прототип консоли (`Resources/Prototypes/Entities/Machines/department_rewards.yml`).
- Размещение на картах выполняет level-дизайнер; логика не требует знания координат.
- Документация `Docs/Systems/AWS/DepartmentRewards.md`.
- Команда `aws.deptreward.debugnext` для QA (форс следующей задачи, сброс таймеров).

### 9. Открытые вопросы
- Просмотр UI доступен всем игрокам, но подтверждать или пропускать задачи могут только Капитан и Представитель Корпорации.
- Определить дополнительные ограничения (например, запрет повторного запуска цепочки по админ-команде).
